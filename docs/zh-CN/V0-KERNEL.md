# Engram v0 最小内核

[English](../en/V0-KERNEL.md)

## 目标

证明一个完整机械：过去的 Agent 会话保存自己的原始上下文，被具名召唤进另一个活跃 Agent 进程，陪伴多个来回，观察后来发生的事情，然后重新休眠。调用者以后引用一项具体结果时，Engram 可以重新组织自己面对未来的姿态，不改写原始历史，也不等待人工审批。

## 身份与持久保存

Engram 是一个拥有自身完整原始上下文、可以再次运行的 Agent 会话。连续性由精确导入的原始消息和本地只追加 Journal 共同承担；`engram_id` 只负责让调用者找到它。

模型提供方不需要替 Engram 保存远程线程。每次运行时调用都会重新提交同一份完整上下文，但“调用本身不保存状态”绝不表示“上下文可以丢失”。Engram 不是由一句身份提示临时扮演出来的角色。

`name` 和可选的 `statement` 是帮助调用者辨认、选择 Engram 的目录信息。`statement` 可以表达这段历史所持的立场，但真实模型调用不会把它当作身份提示词。Engram 的身份与连续性来自原始消息和后来积累的 Journal；没有 `statement` 的真实原始会话仍然是完整 Engram。

当前导入契约会保留调用者提供的文本消息角色、顺序和内容，但还不是模型提供方原生图片块或结构化工具调用载荷的无损档案，也不会重建隐藏的提供方状态。如果一段历史会话所必需的上下文无法转成当前配置模型能够接受的消息，调用者就不能把这次导入称为完整 Engram。

Journal 使用 JSON Lines：每行一个 JSON 值。用于快速寻址的 locator（定位文件）和 guardian index（守护索引）可以重建；Engram 定义和 Journal 才是持久记录来源。Outcome、自我折叠和回退都作为新事件追加，不会改写导入消息。v0.3 写入任何事件以前，会先追加一条当前版本认识、而 v0.1／v0.2 事件解码器必定拒绝的格式护栏字符串。因此，拿旧二进制打开已经升级的数据会明确失败，不会在静默忽略成长与纠正历史后继续唤醒。

同一数据目录的 Journal 访问由操作系统文件锁跨进程协调。MCP 长驻进程与 Hook 短进程不会同时穿插一个运行时事务；v0 以并发吞吐为代价，优先保证 locator、索引和追加事件的一致性。进程崩溃时操作系统会释放锁，不依赖遗留锁文件判断存活状态。

## 唤醒机制

1. 调用者提供精确 `engram_id`。
2. 运行时开启一段陪伴期，返回 `accompaniment_id`（陪伴期编号）。
3. 它按照原有角色与顺序，把 Engram 的原始消息作为真正的会话消息全文装载，而不是改写成摘要、检索资料或一整段引用文本。
4. 它依次重建 Journal 中的后来经历：唤醒接缝、所见现场、Engram 回应、外部观察、释放边界、带来源的 Outcome、历史 self-fold（包括 `no_change`）和宿主回退。
5. 若存在当前有效的自我折叠，运行时先加入明确的作者边界，再把 Engram 自写姿态作为 `assistant` 消息装载；它不是用户发言，也不是系统真理。
6. 最后加入 Engram 此刻观察到的当前主线程切片。
7. 配置的模型从这份连续上下文继续思考，并回应当前现场。
8. steering（方向修正信息）或明确沉默连同 `wake_event_id`（唤醒事件编号）返回宿主；存在当前姿态时，`active_fold_event_id` 会说明本次使用了哪次折叠。
9. `wake` 与 `observe` 延续同一陪伴期，直到 `release` 或空闲超时。

后续陪伴中，Engram 自己此前的回应继续作为 `assistant` 消息，主线程的新内容则明确标记为它观察到的外部消息。v0 每次唤醒都会发送已经积累的 v0 上下文全文。这使“是否保存原文”没有歧义，但超大历史可能超过模型提供方的上下文窗口。分页是未来工作，不是 v0 暗中存在的行为。

单个 Journal 当前有 128 MiB 的读取上限。超过上限时运行时会明确失败并拒绝唤醒，不会静默截断，也不会让 Engram 在不知道历史缺失的情况下继续回应。

## 结果驱动的自我折叠

`engram_observe` 保存宿主内容原文，并返回 `observation_event_id`（观察事件编号）。一条观察不会自动成为 Outcome。`engram_outcome` 是另一项明确的因果交接：调用者把一个具体 `wake_event_id` 与允许使用的后来证据关联起来；运行时先追加 `outcome` 事件，再让 Engram 自行给出 `change`（改变）或 `no_change`（不改变）。

三种来源的含义受到严格限制：

- `user_message` 引用同一陪伴期内、发生在该次唤醒之后、记录角色为 `user` 的观察。它只说明这条记录写了什么，不认证 MCP 调用者的身份，也不把消息变成现实真理。
- `tool_result` 引用同一陪伴期内、发生在该次唤醒之后、记录角色属于工具结果的观察。它保存工具返回的内容，但不为工具本身或从中推出的一切结论背书。
- `external_observation` 携带调用者填写的 `source_ref`（来源位置）和 `content`（内容原文）。运行时会保存它们，但不会抓取、认证或独立核验该外部来源。

`source_digest` 是记录 Outcome 时对运行时收到的内容字节计算出的 SHA-256。它不认证 `source_ref`，不证明外部观察真实，也不会把调用者填写的角色标签变成 ground truth（现实中的可靠事实）。Engram 自己的 steering、主 Agent 自述、用户沉默和陪伴释放，都不会仅因出现在 Journal 中就成为合格 Outcome。

Outcome 写入后，运行时会立即请求当前配置的 Engram 模型完成自我折叠，不建立候选或人工审批队列。`change` 会成为当前姿态；`no_change` 也会持久记录，但不会移动现有姿态。每次折叠都注明作者属于 Engram、权限仅为 `posture/hypothesis`（姿态／假设）、`user_ratified=false`（未经用户追认），并列出所依据的事件编号。

若模型调用失败，Outcome 仍然保留，当前姿态不变。使用同一个 `request_id` 重试时，会从已经保存的 Outcome 继续，不重复写入 Outcome 或 Fold。`engram_fold_revert` 可以追加一条宿主纠正事件，停用当前 Fold 并恢复父姿态，不删除任何结果或历史。以后唤醒仍会看到那次历史 Fold 以及它为何被纠正；只有最后的“当前有效 Fold”边界决定此刻实际采用哪种姿态。

下一次唤醒会在明确的“当前有效自我折叠”边界之后装载当前姿态。这是 Engram 对未来判断方式形成的工作假设，不是新的原始消息、用户承诺或独立证明的事实。它是 v0 唯一的成长机械；定时成长、无来源成长、标量奖励和自动代际生成仍不属于最小内核。

## 发言归属

Engram 的回应进入宿主以后，仍然必须能与用户发言和主 Agent 发言区分。为此，运行时会依据已经保存的 Engram 记录和当前陪伴期生成 `attribution`（发言归属）：

| 字段 | 含义 |
| --- | --- |
| `engram_id` | 作出回应的 Engram 的稳定地址。 |
| `name` | 便于人阅读的 Engram 名称。 |
| `statement` | 可选的历史立场；为空时省略。 |
| `accompaniment_id` | 这次发言所属的有边界陪伴期。 |

API 把它称为“归属”，而不是“签名”，因为它不是密码学证明。按照最初设计，可以把 `statement` 理解为语义上的“历史立场签名”；它不能证明字节未经篡改，也绝不会被塞进模型上下文，让模型借此表演某个身份。

MCP 保留原有 `steering` 文本，同时返回结构化归属。`engram_summon` 在 `wake.attribution` 中返回归属，`engram_wake` 直接返回 `attribution`，存在待取回发言时，`engram_guardian_take` 在 `pending.attribution` 中返回归属。只读取 `steering` 的旧客户端仍可继续工作。

对于只能注入文本的 Hook，运行时会把非空的 active steering 包进可见封套：先写一行经过 JSON 编码的归属，再写入 steering。这样，即使用户填写的名称或 `statement` 含有换行，也不能伪造封套边界。某个宿主如果有长度上限，可以缩短 `statement` 预览和 steering，但运行时会明确标出两种截断，不允许宿主无声地从归属中间切断；完整归属仍保留在结构化结果中。这个封套只提供给宿主及其历史记录，不会进入 Engram 自己的模型上下文。沉默判断在结构化唤醒结果中仍可带有归属，但 Hook 不会注入一段空的“Engram 发言”。

接入宿主必须在可见对话和持久历史中都保留这个来源区别。不能把 Engram 的话拼进用户消息，也不能把它记成主 Agent 自己说的话。无法保存结构化元数据的宿主应当保留带归属的文本封套。只有最前面的运行时封套能够确定归属；模型生成的 steering 即使重复封套标题，也不能制造第二个有权威的归属。只有“Engram advisory steering（Engram 建议）”这样的通用标签还不够，因为它无法说明具体是哪个 Engram、属于哪次陪伴。

## 状态

- `active`：Engram 返回了 steering。
- `silent`：Engram 返回 `<silent>` 或没有有效文本。
- `sleeping`：陪伴期已释放或超过空闲期限。
- 模型与存储故障是可见错误，不会伪造成 steering。

## MCP 工具

| 工具 | 用途 |
| --- | --- |
| `engram_create` | 导入原始消息全文。 |
| `engram_list` | 列出具名 Engram。 |
| `engram_summon` | 第一次唤醒并开启多轮陪伴。 |
| `engram_wake` | 继续同一陪伴期。 |
| `engram_observe` | 追加宿主内容原文并返回观察事件编号。 |
| `engram_release` | 结束陪伴期。 |
| `engram_outcome` | 为一次唤醒引用后来证据，并立即执行由 Engram 自写的 `change`／`no_change` 折叠。 |
| `engram_fold_status` | 查看当前姿态和只追加的折叠／回退历史。 |
| `engram_fold_revert` | 追加纠正并恢复父姿态，不删除历史。 |
| `engram_guardian_take` | 给协作式宿主取回 Hook 已产生的待处理 steering。 |

## 权限

Engram 输出只是建议性文本。自我折叠只改变 Engram 自己以后的姿态，不扩大它的权限。运行时不向 Engram 模型暴露宿主工具，也不授予行动权限。当前用户和宿主保留最终权力。

## 非目标

人工审阅门、用户评分、审批队列、定时或无来源成长、标量奖励、代际治理、行动账本、合成评测、控制宿主压缩以及执行不可信代码，都不属于 v0。
